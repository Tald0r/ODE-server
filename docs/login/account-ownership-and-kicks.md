# Account ownership and kicks

The fixtures named in the Owner column are test groups in `login_server_runtime_tests`
(`tests/login_*_test.cpp`), which link the production `LoginServerRuntime` objects without
process startup ([login lifecycle](overview.md)).

| Rule | Owner | What fails when it is broken |
|------|-------|------------------------------|
| Every login acquisition prepares an owned account identity before writing LOGON; disconnect cleans only that owner, attempts all cleanup steps and retains failed logouts for retry | `LoginAccountOwnership`/`LoginAccountSession` in `login_server_runtime_tests`, plus login/reconnect decision and completion ownership cases | lost partial acquisitions, logout of an unacquired or changed ID, ownership overwritten by a fresh attempt, flush/close failures skipping cleanup, replaced first errors, repeated successful logout or allocation after acquisition acknowledgement |
| Login retirement detaches table/poll membership before cleanup, closes locally despite failure, and owns failed account logouts until a due retry succeeds | `LoginPlayerRetirement` in `login_server_runtime_tests` over explicit time/actions, production loops and incoming-reply handlers | closed players left registered, lost failed logout owners, allocating adoption, early/repeated successful logout, stale readiness or reused-descriptor closure, last-player removal failure, lock misuse or leaked scoped cleanup |
| A handler's `ProtocolException` or `ConnectException` reaches `LoginPlayerManager` as it is; anything else a handler throws is logged by its type and the packet's id and size to `LoginPlayerError.txt` and becomes a `DisconnectException`, retired with its reply flushed like a logout, so it never leaves `processCommands` | `LoginHandlerFailure` in `login_server_runtime_tests` over a real loopback connection and a child-registered handler that queues a reply before it throws | a handler's `Throwable`, `DatabaseError` or `std::exception` reaching the main thread's `ClientManager::run`, the throwing player left registered, a logout's reply not flushed or a lost send's flushed |
| Login connections retain ownership through registration and end their local session before destruction; scoped managers restore reconnect bindings | Login runtime `LoginConnection` cases over forwarded sockets, allocation faults, occupied slots, real I/O and counted packet history | leaked refusal/constructor resources, changed buffer sizes, failed retry, skipped packet cleanup, database logout during resource teardown or a dangling context binding |
| Incoming game-connection replies consume only a matching pending account under one manager lock; reconnect failures still retire without flushing a partial reply | `LoginIncomingReply` in `login_server_runtime_tests` over explicit sender/retirement actions and both production handlers | late replies closing another phase, assertions on stale errors, wrong reconnect fields, send/reporting failures skipping cleanup, lost pending logout ownership, duplicate cleanup, lock misuse or leaked allocation failures |
| Selected-character incoming requests prepare owned destination/packet/write inputs before publication; send failure restores phase/address, and successful dispatch precedes both location writes | `LoginIncomingRequest` in `login_server_runtime_tests` over explicit catalogue/configuration/repositories, real UDP and reply composition | silent unsent requests for custom users, invalid endpoint/field publication, changed packet or port policy, dangling catalogue/request references, diagnostics blocking send, incorrect rollback after persistence failure, lost account ownership or leaked allocation failures |
| Login kick preparation uses explicit repositories, validates last-location fields and publishes only a complete target; missing data is refused before datagram dispatch | `LoginKickPreparation` in `login_server_runtime_tests` over real session state and refusal serialization | uninitialized or wrapped routing, a lost cached slot, empty-name targets, partial cache publication, early identity reset, changed exception policy or leaked failure/retry storage |
| A saved kick target owns its account identity and location independently of live selection; failed replacement preserves borrowed pointers, and verification reads only the current account's entry | `LoginKickCache` and `LoginKickPreparation` in `login_server_runtime_tests`, including the production verify handler | stale-account queries or verification, selection overwriting saved routing, partial replacement, leaked entries, cache clearing before a successful refusal or failed cleanup/retry |
| Kick dispatch prepares owned server-1 destinations from occupied groups before sending, and publishes its wait only after all supplied sender calls return | `LoginKickDispatch` in `login_server_runtime_tests`, including real catalogue loads, allocation failures, packet serialization and production UDP delivery | skipped sparse/boundary groups, lookup failures after partial sends, waiting on an empty catalogue, stale borrowed destinations, premature status/deadline changes or failed exception cleanup/retry |
| Login datagram sends validate canonical IPv4 endpoints and require a complete local send; failures remain observable despite broken diagnostics and a failed kick disconnect cannot log off the existing session | `LoginDatagramSend` and the production failure case in `LoginKickDispatch`, in `login_server_runtime_tests` | narrowed ports, ambiguous or truncated addresses, false success after zero/partial sends, diagnostics hiding failure, leaked partial frames or existing-account logout after a failed send |
| Kick verification admits only a waiting session with a matching account-owned character, and a scoped manager lock protects lookup and completion | `LoginKickVerification` in `login_server_runtime_tests` over real managers, supplied completion and allocation faults | completion after the pending phase, stale-account/name matches, narrowed descriptor access, an exception leaving the manager locked, failed acquisition unlocking the caller's lock or damaged cleanup/retry |
| Kick retries use explicit time and request/completion actions; only successful resends for the same pending attempt count, and fresh attempts reset their count | `LoginKickRetry` in `login_server_runtime_tests`, including production polling, refusal and allocation failures | completion after refusal or an account/target/attempt change, inherited counts, early retries, unbounded counts after completion failure, lost exception identity or a refused production attempt stuck waiting |
| Kick-login completion uses explicit persistence, statistics time and diagnostics, fully initializes replies, and suppresses a refused account only after sending | `LoginCompletion` in `login_server_runtime_tests` over actual packet serialization and retry/verification composition | uninitialized reply fields, refusal disconnect logging off another session, early phase publication, changed write/time ordering, diagnostics replacing the result/cause, hidden partial effects or leaked allocation failures |
